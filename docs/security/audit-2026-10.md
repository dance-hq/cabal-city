# Cabal security audit — October 2026

Scope: the web app (`cabal.city`, Next.js on Vercel), the database rules and storage (Supabase), the desktop app (`desktop/`, Electron) and its published installers v0.1.0–v0.1.3, the GitHub repository and its workflows.
Baseline: `main` at `a53f414` and production deployment `dpl_HZXLup52bGu9SB3F2iFJWu5SwidN`. Fixes are on branch `v0/build-cabal-application-093736a4`.

This is one audit by one reviewer, not a certification. Where something wasn't tested, it says so.

## A. Executive summary

**How secure is Cabal today?** The web app is in good shape for a product this young. Every table has row-level security, and an adversarial test suite run against the real production rules found one gap, now fixed. No secrets have ever been committed. Direct messages are end-to-end encrypted, and the privacy page describes accurately what is and isn't. The weak part is the desktop app: every published installer is **unsigned**, and the shipped builds leave several Electron safety switches ("fuses") off.

**Biggest risks**

1. **Unsigned installers and a weakly anchored update channel.** Nothing proves a download came from the Cabal team. Windows and Linux auto-updates trust whatever the GitHub release says. Anyone who can publish a release (five admins, or a stolen token) could push code to every installed copy.
2. **One compromised admin account reaches every user.** `main` doesn't require a review or passing checks before code lands, and it deploys to production automatically.
3. **No monitoring or alerting.** If something went wrong, nobody would be told.

**Are accounts and private messages adequately protected?** Mostly, yes. Sign-in uses one-time email codes, stored only as keyed hashes. Sessions are HttpOnly cookies. The authorization suite (41 checks after the [second pass](#second-pass-same-day), all passing) confirms people can't read conversations they aren't in, act as someone else, or give themselves admin. DMs are encrypted on the device. Two caveats remain. The server still *accepts* an unencrypted DM from a modified client (finding CAB-10, fix ready, needs your approval). And 51 DMs sent before encryption existed are stored in plain text (disclosed on the privacy page). Room and team messages aren't end-to-end encrypted, which is by design and disclosed.

**Are the downloadable apps trustworthy?** Not yet in a way a stranger could verify. Code-wise, the app's sandboxing is solid. But the installers carry no publisher signature, and v0.1.0–v0.1.3 have no published checksums or provenance. The next release from this branch adds checksums, signed build-provenance attestations and the fuse hardening. Signing needs certificates, which you have to buy.

**Would I recommend a new user install Cabal today?** The web app: yes, for the current community. The desktop app: only for people who know the team personally and got the link from them, until signed builds ship.

**Must be fixed immediately:** nothing is actively exploitable at critical severity. Before any public push of the desktop app: ship a release from this branch, sign the macOS and Windows builds, and require reviews on `main`. Details in [F](#f-release-readiness-verdict).

**Unknown or unverified:** settings in the Supabase, Vercel and GitHub organization dashboards I couldn't reach (backups, network restrictions, team members, 2FA enforcement, repository secrets, Dependabot and code-scanning alerts). Also untested: the macOS and Windows binaries at runtime (only the Linux build was run), an independent review of the encryption protocol, and load or denial-of-service resistance. Full list in [What was not tested](#what-was-not-tested).

### CAB-01 · P1 · Desktop installers are unsigned on every platform
- **Component:** release pipeline, `desktop/package.json` (`build`), `.github/workflows/desktop-release.yml`
- **Description:** v0.1.0–v0.1.3 are published without a publisher signature. The Windows installer has no Authenticode signature. The macOS app has only the ad-hoc signature the linker adds (no Developer ID, not notarized). The Linux `.deb` and AppImage are unsigned.
- **Impact:** users can't tell a genuine download from a modified one. macOS Gatekeeper and Windows SmartScreen warn, which teaches people to click through warnings. Unsigned Mac apps can't auto-update (Squirrel.Mac requires a signature), so Mac users never get security fixes unless they download again by hand.
- **Evidence:** downloaded the v0.1.3 assets. `Cabal-0.1.3-windows-setup.exe` has a PE security directory of size 0. In `Cabal-0.1.3-mac-arm64.zip`, the code signature superblob has no CMS blob (`0xfade0b01`), contains no "Developer ID"/Apple certificate strings, and `_CodeSignature/CodeResources` has no entries.
- **Verify:** `osslsigncode verify` / `signtool verify /pa` on the exe; `codesign -dv --verbose=4` and `spctl -a -vv` on the app.
- **Remediation:** buy an Apple Developer ID and set up notarization; set up Azure Artifact Signing for Windows. The workflow already supports both and fails the release if a configured signature doesn't come out valid (`docs/desktop.md` → Signing). Optionally sign the `.deb` / publish a GPG-signed `SHA256SUMS`.
- **Status:** open. Needs paid certificates and your approval.

### CAB-02 · P1 · Auto-updates trust the GitHub release alone
- **Component:** `desktop/src/main.cjs` `startUpdates()`, `electron-updater` with the `github` provider
- **Description:** the app checks GitHub Releases every six hours and installs what `latest*.yml` points to. Without code signing, the only check is that the file's SHA-512 matches `latest*.yml`, and both come from the same release. There is no publisher check on Windows (that needs a signature) and no independent anchor.
- **Impact:** whoever can create or edit a release controls every installed Windows and Linux AppImage copy within hours. That includes any of five repository admins, a leaked token with `contents: write`, or a compromised workflow. Releases are mutable (CAB-16), so assets can be swapped after publication.
- **Evidence:** release API shows `immutable: false`. The `latest.yml` SHA-512 matches the exe. The exe has no signature (CAB-01). Five collaborators have the admin role, and the tag ruleset lets admins bypass it.
- **Remediation:** sign (CAB-01). Signed Windows installs then refuse updates from a different publisher. Turn on immutable releases. Require reviews (CAB-15). Done on this branch: every tagged release now gets `SHA256SUMS.txt` and a signed build-provenance attestation, so a download can be traced to this repo, workflow and commit (`gh attestation verify`).
- **Status:** partly fixed. Provenance applies from the next tag. Signing and immutable releases are open.

### CAB-03 · P1 · Shipped desktop builds leave Electron fuses off
- **Component:** `desktop/package.json` → `build.electronFuses` (was absent)
- **Description:** v0.1.3 ships with the stock Electron fuse settings: `RunAsNode` on, `EnableNodeOptionsEnvironmentVariable` on, `EnableNodeCliInspectArguments` on, `EnableEmbeddedAsarIntegrityValidation` off, `OnlyLoadAppFromAsar` off, `GrantFileProtocolExtraPrivileges` on.
- **Impact:** other software on the machine can start the Cabal binary as a plain Node.js interpreter or attach a debugger, borrowing Cabal's identity. Once the app is signed, that identity includes its signature, its macOS privacy permissions and any firewall exceptions. The app's code (`app.asar`) can be modified without detection. This is P1 because signing is planned, and signing makes the binary worth borrowing.
- **Evidence:** read the fuse wire from the v0.1.3 macOS Electron Framework (sentinel `dL7pKGdnNz796PbbjQWNKmHXBZaB9tsX`). Built this branch for Linux: `@electron/fuses read` shows the new values. `ELECTRON_RUN_AS_NODE=1 ./cabal-desktop -e …` prints nothing. On the same binary with `RunAsNode` flipped back on, it prints `RAN AS NODE: v24.22.0`. The hardened build starts and stays running under a virtual display, so asar integrity validation doesn't break launch.
- **Tests:** `desktop/test/rules.test.cjs` → "released builds turn off the Electron features an attacker could borrow".
- **Status:** fixed in code. Reaches users with the next release.

### CAB-04 · P2 · Desktop trusted any local `file:` page with the bridge
- **Component:** `desktop/src/main.cjs` (`will-navigate`, bridge sender check, popout windows)
- **Description:** navigation allowed, and the desktop bridge trusted, any URL starting with `file:`, not just Cabal's offline page. A server-side redirect away from Cabal also wasn't blocked.
- **Impact:** if an attacker could get the main window onto a local or foreign page (a future open redirect, or a crafted link), that page would sit next to `window.cabalDesktop`. Exposure was limited, because the bridge only offers settings, badge and window controls, with no file or shell access.
- **Fix:** `isOfflinePage()` compares the exact file path of the bundled offline page. Bridge calls are accepted only from the main window's `webContents`. Main-frame `will-redirect` to anything outside Cabal's origins is blocked in the main and popout windows.
- **Status:** fixed in code. Ships with the next release.

### CAB-05 · P3 · Global shortcut accepted everyday combinations
- **Component:** `desktop/src/rules.cjs` `normalizeSettings` / settings patch
- **Description:** any string up to 60 characters was registered as a system-wide shortcut, including `Ctrl+V` or a bare key.
- **Impact:** a script running in Cabal's page (that would need an XSS first) could take over paste or copy in every app on the computer.
- **Fix:** `validShortcut()` requires a real modifier and exactly one key, and refuses one-modifier combinations of common keys (copy, paste, undo, quit and so on). Tests in `desktop/test/rules.test.cjs`.
- **Status:** fixed in code. Ships with the next release.

### CAB-06 · P2 · Lock-in realtime topic joinable without signing in
- **Component:** `components/cabal/work-session.tsx`, `public.can_use_topic`, migration `0032_private_lock_in_topic.sql`
- **Description:** the "someone locked in, look again" ping used a public Realtime channel, while all conversation channels are private.
- **Impact:** anyone holding the public anon key (shipped in every page) could listen to when members start focus sessions and send fake pings, which make every open client refetch. No message content or identities are carried.
- **Evidence:** anonymous Realtime client joining `lock-ins:<community>` → `SUBSCRIBED`; joining a private `chan:<id>` → `CHANNEL_ERROR Unauthorized`. The authorization suite's check failed before 0032 and passes after.
- **Fix:** the client joins the channel as private. Migration 0032 lets only active members of that community use the topic. It's additive and was applied to production alone, recorded in both migration ledgers.
- **Remaining:** nothing, and do **not** turn off public channel access in Supabase. *Correction (2026-10-22):* this report first said to turn it off, but the main live-update channel (`cabal-db:<user>`) and the device-approval channel (`e2ee:<user>`) are public `postgres_changes` channels, so that switch would stop live messages. They're safe as public channels, because Realtime filters `postgres_changes` through row-level security. Every broadcast topic Cabal listens on is private. Production still allows public access (checked after the deploy).
- **Tests:** `tests/integration/authorization.test.ts` → realtime.

### CAB-07 · P2 · Sign-in code hashing fell back to a fixed key
- **Component:** `app/api/auth/code/route.ts`
- **Description:** emails and IPs in `auth_code_requests` are stored as HMAC hashes. If `SUPABASE_JWT_SECRET` was unset, the key silently became the string `cabal`.
- **Impact:** on a misconfigured deployment (self-hosters especially), a database leak would let anyone recover emails and IPs by hashing guesses. Production has the secret set, so production wasn't affected.
- **Fix:** use the JWT secret, or the service-role key; otherwise refuse to run. Test in `tests/unit/request-safety.test.ts`.

### CAB-08 · P2 · Cookie-authenticated POSTs didn't check Origin
- **Component:** `app/api/{auth/code,session/bootstrap,account/delete,feedback,reports/sealed}/route.ts`, new `lib/same-origin.ts`
- **Description:** these routes relied only on the session cookie's SameSite=Lax attribute to stop cross-site requests.
- **Impact:** low today, because Lax already blocks cross-site POSTs in current browsers. But account deletion and session setup deserve a second lock (older browsers, same-site subdomains, future cookie changes).
- **Fix:** refuse any POST whose `Origin` names another host (`403`). Requests without an Origin carry no browser cookies and pass. Verified on the dev server: a foreign Origin gets 403, a same-site signed-out request gets 401. Unit tests cover lookalike hosts, `null` origins and proxies, and assert every listed route uses the check.

### CAB-09 · P3 · SSRF guard missed some IPv6 transition ranges
- **Component:** `lib/safe-fetch.ts` (link previews)
- **Description:** the guard already checks the resolved IP at connect time and blocks private IPv4/IPv6. It didn't cover IPv4-compatible `::a.b.c.d`, NAT64 local-use `64:ff9b:1::/48`, `2001::/23` (Teredo and other IETF assignments), site-local `fec0::/10` or the 6to4 relay anycast `192.88.99.0/24`. A connection reset mid-body was also an unhandled error.
- **Impact:** a crafted DNS answer could aim a preview fetch at an internal address on networks that route those ranges. Not reachable on Vercel as far as I know, but self-hosters may differ.
- **Fix:** ranges added, and response errors end the fetch. 20 address cases in `tests/unit/request-safety.test.ts`, plus the existing `link-preview` tests.

### CAB-10 · P2 · Server still accepts unencrypted DMs
- **Component:** `send_message*` RPCs; held-back migration `0018_require_encrypted_dms.sql`
- **Description:** current clients always encrypt DMs (since 2026-10-22, 13 DMs sent, all encrypted, none plain). But the database still accepts a DM with a plain body.
- **Impact:** a modified or buggy client could store a DM in plain text, readable by the operator, and the recipient would see it labelled "sent before encryption". This contradicts the promise that new DMs are always encrypted.
- **Remediation:** apply 0018. Every desktop version loads the live web app, so no supported client sends plain DMs. It changes behavior (plain DM sends are refused), so it needs your approval. Apply it alone, never via `scripts/db.mjs migrate`.
- **Status:** open, awaiting approval.

### CAB-11 · P3 · Pre-encryption DMs stored in plain text
- 51 DMs from 2026-10-21, before encryption shipped, are stored as written. The privacy page says so ("Messages that were sent before encryption arrived stay as they were"), and the app labels them. Options: leave them (current, disclosed), or offer each person a one-tap "delete my old unencrypted DMs". That's a product decision, so I haven't touched them.

### CAB-12 · P3 · Content-Security-Policy mostly report-only
- **Component:** `next.config.mjs`
- **Done:** enforced `object-src 'none'; base-uri 'self'; frame-ancestors 'self'; form-action 'self'`, none of which can break the app. The full policy (default-src, script/connect/img/media sources) is sent as `Content-Security-Policy-Report-Only`.
- **Remaining:** `script-src` keeps `'unsafe-inline'` because Next.js hydration uses inline scripts. Next step: nonces via `proxy.ts`, then enforce the full policy once production reports are clean.

### CAB-13 · P2 · Known-vulnerable packages in the production tree
- **Before:** `pnpm audit --prod` → 4 high, 1 moderate: nanoid, browserslist (×2), source-map-js, baseline-browser-mapping, all pulled in by `next`'s build tooling. Also postcss < 8.5.31 (CSS stringify XSS). `shadcn` (a CLI) sat in `dependencies`.
- **Exploitability:** low. These run at build time on our own inputs, not on user input.
- **Fix:** pnpm `overrides` to patched same-major versions (`pnpm-workspace.yaml`), postcss ^8.5.31, `shadcn` moved to devDependencies. **After: `pnpm audit --prod` = 0.** `pnpm install --frozen-lockfile` passes.
- **Accepted:** 59 dev-only advisories, every one through the `shadcn` CLI (never shipped). In `desktop/`, 8 moderate advisories in the electron-builder chain (build machine only; npm's suggested "fix" is a downgrade).
- CI now runs `pnpm audit --prod --audit-level high` and dependency review on pull requests. Dependabot is configured.

### CAB-14 · P2 · Workflows over-privileged, actions unpinned, release used a shared cache
- **Component:** `.github/workflows/*.yml`
- **Before:** the release workflow granted `contents: write` to every job. Actions were referenced by moving tags. Checkout left the token in `.git/config`. Release builds restored the npm cache that other workflows (including pull requests) can write, which is a known path for poisoning an installer.
- **Fix:** workflow-level `contents: read`, with write granted only to the jobs that publish. Every third-party action is pinned to a commit SHA. `persist-credentials: false`. No dependency cache in release builds. New `security.yml` runs CodeQL (JS/TS and Actions, security-extended) on PRs, pushes and weekly, plus dependency review on PRs. `dependabot.yml` covers npm (root and desktop) and Actions.
- **Verify:** YAML parsed for all workflow files. CodeQL and dependency review only run on GitHub, so they **run for the first time when this branch is pushed**.

### CAB-15 · P2 · `main` requires no review or checks; five admins
- **Evidence:** ruleset "Protect main" blocks only deletion and force-push. No classic branch protection. Five collaborators have the admin role, and the release-tag ruleset lets admins bypass it. `sha_pinning_required: false`.
- **Impact:** one compromised account can put code on `main` (auto-deployed to production) or tag a release (auto-updated to desktop users) with nobody else seeing it.
- **Remediation (needs approval, changes how the team works):** require a pull request with one approval and the `CI` and `Security` checks on `main`. Reduce admins to the people who cut releases. Enforce 2FA at the org (couldn't verify current state). Turn on "Require actions to be pinned to a full-length commit SHA".

### CAB-16 · P3 · Releases are mutable; no checksums for v0.1.0–v0.1.3
- Release assets can be replaced after publication. Turn on immutable releases (Settings → General → Releases). From the next tag, the workflow publishes `SHA256SUMS.txt` plus attestations. Existing releases have none. The cleanest path is to publish v0.1.4 from this branch and point everyone at it.

### CAB-17 · P2 · No DMARC or apex SPF: `@cabal.city` mail can be spoofed
- **Evidence (public DNS):** no `_dmarc.cabal.city` record and no SPF at the apex. Resend's DKIM (`resend._domainkey`) and the `send.` return-path SPF exist. CAA limits certificates to Let's Encrypt, Google and Sectigo (good).
- **Impact:** anyone can send mail that claims to be from `@cabal.city`, for example fake sign-in code emails linking to a lookalike site. Many receivers will deliver it.
- **Remediation (DNS, your action):** add `_dmarc.cabal.city TXT "v=DMARC1; p=none; rua=mailto:<your-address>"`, watch reports for two weeks, then move to `p=quarantine` and later `p=reject`. If the apex itself never sends mail, add `cabal.city TXT "v=spf1 -all"`.

### CAB-18 · P2 · No error monitoring, alerting or incident runbook
- No error tracking or alerting packages. Nothing alerts on unusual sign-in volume, admin actions, realtime abuse or failed releases. Logs live only in Vercel and Supabase.
- **Done:** `docs/security/release-checklist.md` (per-release checks plus a short incident playbook).
- **Recommended:** enable Vercel log drains or error reporting, Supabase alerts for auth spikes, and a GitHub notification on new releases and tags.

### CAB-19 · P3 · `anon` role keeps default table grants
- Supabase's default grants give `anon` table privileges on most public tables. Row-level security blocks all of it: tables without an anon policy return nothing, and the suite confirms signed-out visitors read nothing private and can't call any security-definer function. Revoking the unused grants would be defense in depth. Recommended as a migration once reviewed, not done here because it touches permissions broadly.

### CAB-20 · P3 · Small leaks and footguns
- `x-powered-by: Next.js` removed (`poweredByHeader: false`).
- `.gitignore` only ignored `.env*.local`, so a plain `.env` could be committed. Now every `.env*` is ignored except `.env.example`.
- **Secrets check:** the live values of the six server-side secrets were searched across all 179 commits and the working tree (compared in memory, never printed): 0 hits. GitHub secret scanning, push protection and validity checks are on.

### CAB-21 · P3 · Encryption claims didn't state the web-delivery and first-contact limits
- **Component:** `app/privacy/page.tsx`, `lib/docs.ts` (`ENCRYPTION_SCOPE`)
- **Description:** the privacy page said neither admins nor the team "can read" DMs. That's true of the stored copies, but the code that encrypts is served by cabal.city (the desktop app loads the same web app). A compromised deployment could ship code that reads a message before it's sealed. This is the known limit of all web-delivered encryption. Public keys also come from the server: the "security code changed" notice only catches a swapped key if you already had the old one, and comparing codes is what rules out a swap on first contact.
- **Impact:** none technical. It's about honesty: the brief asks for no overstated encryption claims.
- **Fix:** the privacy page now says the stored copies can't be read and that the protection relies on cabal.city serving the published open-source code. The developer docs list both limits.

### CAB-22 · P3 · "Maintainer" means admin of any community
- **Component:** `public.is_maintainer()` (migration 0014)
- **Description:** maintainers can post and delete entries in the global "Today's Ship" log, set idea statuses and links, see hidden ideas and manage opportunities that apply everywhere. `is_maintainer()` is true for an admin of *any* community.
- **Why it's fine today:** one deployment runs one community (production has exactly one). Nobody can create a community from the client (no insert policy, no RPC). `join_community` always inserts a plain member, and admin only comes from the server's admin email list. The suite now checks all three.
- **Before adding a second city or private community:** make maintainers an explicit list (a `maintainers` table or app metadata set by the server), so a new community's admins don't gain control of the shared board.

### Second pass (same day)
A second reviewer re-checked this report against the code and production, with nothing new on `main` since the baseline.
- **Re-verified:** `tsc` clean · vitest 25 files, 244 passed · `pnpm audit --prod` 0 · desktop 22/22. Production still serves the audited deployment (`/api/version` = `dpl_HZXLup52bGu9SB3F2iFJWu5SwidN`, `x-powered-by` still present), so none of the web fixes are live yet.
- **Function coverage:** 96 security-definer functions are executable by signed-in users, and 42 were exercised by tests. Each of the other 54 was read on the live database. Every one checks membership, admin, maintainer or team ownership through helpers built on `auth.uid()`, or acts only on the caller's own rows. No holes were found. Nine checks were added (41 total, all passing, 0 rows left behind): ten admin-only functions refuse members with exactly `42501` and don't refuse the admin; maintainer functions refuse members; joining never grants admin; pending events stay out of other members' calendars; outsiders get nothing from board, channel or invite-code functions; `member_places` never reveals a private team; only owners rename, change the welcome note or cancel invites; team-image folders are owner-only; nobody can approve or decline another person's device request or write their key backup.
- **Stored XSS through links:** no `dangerouslySetInnerHTML`, `innerHTML` or `eval` anywhere in the app or desktop code. Message links go through `safeHref` (http/https only). Every user-supplied URL column in the live database has an `http(s)` check: calendar, opportunities, submissions, profile links, avatars, team images, GitHub links.
- **Encryption protocol (code review, not a formal cryptographic review):** P-256 ECDH; HKDF-SHA-256 keys per message and per file; AES-GCM with random 96-bit IVs; conversation, message id, author and key ids bound as AAD; length padding; 120-bit recovery key; Web Crypto only. Device linking commits to the requester's nonce before the approver answers and checks it before showing the 6-digit code. Peer keys are trust-on-first-use with a visible "security code changed" notice. Nothing exploitable found. Known limits are documented (CAB-21). Private keys are stored extractable in IndexedDB (they're needed for backups and device linking), so an XSS on cabal.city could take them. That makes CSP enforcement (CAB-12) more important.
- **Desktop deep links:** `cabal://` accepts only `c/<uuid>` and `join/<invite code>`. Nothing from a link reaches the shell, the filesystem or a URL load outside Cabal.
- **Link previews:** sign-in required, per-person rate limit, cache, 512 KB / time / 4-redirect caps, connect-time IP check.
- **CI checks haven't run on this branch:** `CI` and `Security` (CodeQL, dependency review) only trigger on pull requests and pushes to `main`, and no pull request exists for this branch yet. Opening one runs them before merge.

### Verified without findings
- RLS on all 32 public tables. Tables with no policies (`auth_code_requests`, `cabal_migrations`, …) are deny-all by design.
- All SECURITY DEFINER functions pin `search_path`. Only four trivial trigger/helper functions are executable by `anon`.
- Storage: `attachments` is private and readable only once a message row claims the file. `avatars` and `team-images` are public by design, and writable only in your own folder or as a team owner.
- Supabase Auth: email only, public sign-up disabled (accounts are created by the server's code flow), no anonymous sign-ins, no auto-confirm.
- Production headers: HSTS (2 years), `nosniff`, `X-Frame-Options: SAMEORIGIN`, a strict referrer policy and a Permissions-Policy denying camera, microphone and geolocation. Apex redirects to `www`. Signed-out API calls get 401.
- Desktop runtime: every window uses `sandbox`, `contextIsolation`, no `nodeIntegration`. Web permissions are limited to notifications and sanitized clipboard write, for Cabal's origins only. Links outside Cabal open in the browser, `https`/`http`/`mailto` only. macOS entitlements are just `allow-jit` and `network.client`.
- Privacy and terms pages match the implementation (room and team messages described as not end-to-end encrypted, legacy DMs disclosed).

## F. Release readiness verdict

### CONDITIONAL GO

**For:** the web app at cabal.city for the current invite-sized community, and desktop downloads shared directly with people who know the team, **once v0.1.4 is released from this branch**.
**Not for:** promoting the desktop app to the public (launch posts, directories, "download Cabal" to strangers). That's a **NO-GO until CAB-01 (signing) and CAB-15 (required reviews) are done**.

**Why it's a GO for that scope (evidence):** authorization holds against 32 adversarial checks on the production rules. Every table has RLS. No secrets are in history. DMs are encrypted on the device. Production dependencies have no known advisories. The desktop runtime is sandboxed, and the only gap found in the web app is fixed.

**Conditions, in order:**
1. Merge and deploy this branch (web fixes go live). Done 2026-10-22. Leave Supabase's Realtime public access on (see the correction under CAB-06).
2. Tag **v0.1.4** to ship the hardened desktop build with checksums and provenance. Ask Mac users to download it by hand once (they can't auto-update unsigned).
3. Approve and apply **0018** so the server refuses plain DMs (CAB-10).
4. Add DMARC (CAB-17).
5. Before any public desktop push: signing for macOS (Developer ID + notarization) and Windows (Artifact Signing), required reviews on `main`, fewer admins, immutable releases.

- **Dashboards I had no access to:** Supabase (JWT expiry, refresh rotation, network restrictions, backups/PITR, Realtime public-channel setting, project members), Vercel (team members, env-var access, deployment protection), GitHub org (2FA enforcement, Actions secrets, existing Dependabot, secret-scanning and code-scanning alerts — the API returned 403).

- **Load, rate-limit effectiveness at scale and denial of service.**
- **Live attacks against production beyond read-only checks.** All authorization tests ran inside a rolled-back transaction, and no production account was touched.
- **CodeQL and dependency review** haven't run yet. They run when this branch reaches GitHub.
